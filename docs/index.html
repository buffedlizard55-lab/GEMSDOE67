Why the family's best file scored 0.2778 — and whether we can beat it

The metric is a budget, not a beauty contest. The official score is a distance-weighted Tversky index (α = 0.2, β = 0.8, 300 m triangular kernel): DTI = TP_w / (TP_w + 0.2·FP_w + 0.8·FN_w). Algebraically DTI = T / (0.2(T+S−M) + 0.8|G|), so every emitted pixel that does not raise the covered-truth credit T costs 0.2 of denominator mass, while each uncovered truth pixel costs 0.8. A dot earns its place only above the break-even credit k > 0.2·DTI (≈ 0.055 at today's scores).

The 0.2778 rung is allocation-side optimisation. The family's score ladder — h19-5 solid 0.1922 → dotted d1.5 0.2477 → dotted d2.8 0.2600 → h27-4 0.2708 → h33-2-B2 0.2778 (ORGANIZER-CONFIRMED) — removed mass that was already covered (thinning a surface to dots) and then pruned flank dots within 200 m of the mapped catalogue. Each step raised credit per emitted pixel on the same detector family. The arithmetic of diminishing returns is visible in the rungs themselves: pruning alone was worth +0.0070.

Yes — beating 0.2778 is possible, but only detector-side. At the same emitted mass the public leader (0.3262 verified read 2026-10-04; the brief quotes 0.3195 for the current #1 — see irregularity IR-67-LB-01) needs ~25% more mean credit per pixel than the h19-5 surface delivers. That credit must come from pixels the catalogue does not already cover: unmapped segments near mapped tips (published tip under-mapping runs to ~500 m per fault in one seismic array and 100–200 m of DEM truncation in a rift), blind splays, and buried fault zones with no surface expression. This repository's lane is built for exactly that: an axial-orientation head + tip/junction head with geometry-aware decoding (Batra et al., CVPR 2019) that extends traces past mapped tips along predicted strike where evidence persists.

What the numbers say today. On the shared hide-and-recover instrument (HOLDOUT-DTI, evaluator gems57-pooled-hide-v2, 22893 withheld positive pixels, 2 draws × 4 quadrants), the full lane beats its own per-pixel ablation at matched pipeline settings: paired Δ = 0.00964 (95% CI [0.00394, 0.01543]), and tip-adjacent recovery rises from 0.0273 to 0.0426 (+56% relative) on 7854 tip-adjacent withheld pixels. That is the gate the brief demanded before a weekly slot may be considered. Absolute HOLDOUT-DTI here is not comparable to leaderboard scores — the hidden organiser truth is not our truth.

The portal error “Predicted values must be in range [0, 1]” — why it happens and why this file is safe

The message fires for two different reasons, and both are fixed here:

  • Mechanism 1 — nodata sentinels. The GeoDAWN feature stack uses -3.4028234663852886e+38 as nodata. Any pipeline that writes that sentinel through to the submission puts values outside [0, 1] in the file. This file contains no sentinel values at all.
  • Mechanism 2 — NaN handling. A file with NaN outside the footprint is a legitimate competition representation (the sample submission uses it), but a validator that computes min ≥ 0 and max ≤ 1 over the raw array rejects it because NaN comparisons are false. The file offered here is all-finite: min 0.0, max 1.0, zeros outside the footprint, no nodata tag. It cannot trip either mechanism.

The receipt that proves it is generated by re-reading the written bytes (scripts/validate_submission.py over the shared gems57.validate/gems57.gates checks) and is shipped next to the download. A sample-faithful NaN-outside twin is also generated for completeness.
