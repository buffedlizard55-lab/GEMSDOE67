The release checklist

  1. Train a new model in this lane; never copy or rename a previous submission.
  2. Pass feature leakage screens and buffered whole-segment hide-and-recover evaluation. Beat the comparable holdout best and improve masked-tip recovery.
  3. Screen the production surface against every registered raster before node placement. Stop on duplicate correlation.
  4. Place nodes, repeat correlation and 3 px overlap checks, and compare hashes and actual pixels against all prior rasters. An incomplete registry is not a pass.
  5. Normalize model output to [0,1] before writing. Use the shared writer to create a single-band float32 GeoTIFF matching the sample’s EPSG:32611, shape and 100 m transform. Reject nonfinite or out-of-range in-footprint values. Finite zeros outside are used by the shared writer.
  6. Run the on-disk validator and bind its receipt to the artifact’s SHA-256. A format-valid file is not yet organizer-accepted.
  7. Only then publish a one-click TIFF download, unique submission name, short note and full run card. A separate selector approves any actual weekly slot.

When an approved file is available

  1. Download the actual .tif using the approved download button. Do not download the HTML page, this guide, the run card or a prior raster.
  2. Check that the filename and SHA-256 match the published receipt. Confirm all gates are green, the inventory is complete and the current weekly cap allows a slot.
  3. Open the DrivenData competition, review the current rules and use its submission form.
  4. Choose the TIFF as “File to submit.” Copy the published short note (at most 140 characters). A ZIP is acceptable only if current rules permit it and it contains exactly one TIFF.
  5. Submit only with selector approval. Save the organizer receipt and artifact hash before calling any result ORGANIZER-CONFIRMED.

The competition website and current weekly cap could not be verified from this network. These steps do not represent a submission or acceptance.

About “Predicted values must be in range [0, 1]”

The error alone does not identify the cause. Check actual on-disk values, not just array values before export. Negative nodata sentinels, infinities, out-of-range predictions and NaN handling need inspection. Do not blindly clip a suspect file and call it ready. Our shared writer rejects invalid values before publishing any output.
