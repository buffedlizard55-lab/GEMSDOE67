How to submit, exactly

  1. Open the submission page: drivendata.org/competitions/306/competition-doe-gems/submissions/
  2. Press New submission → File to submit → choose gemsdoe67-ovtr-ml-cover-tau3p0-20261012-nan.tif (or gemsdoe67-ovtr-ml-cover-tau3p0-20261012.zip).
  3. In Note (optional) paste: GEMSDOE67 OVTR | HGB head on 23 evidence channels -> greedy 3 px kernel-cover of q>=0.3, 167597 dots; pooled HOLDOUT-DTI 0.2691 (4 folds, 60594 withheld px); UNSCORED
  4. Press Submit. The organizer validates CRS, shape, geotransform, dtype and the [0, 1] range. This file was re-read from disk by tifffile and by GDAL before being published; the receipt is downloads/checks-gemsdoe67-ovtr-ml-cover-tau3p0-20261012.json.
  5. Record the returned score in the ledger. Until that happens, every number in this repository is a holdout number and is labelled as one.

The portal error "Predicted values must be in range [0, 1]"

It has two distinct causes, both measured in this checkout:

NaN nodata tag while a validator ignores the tag and ranges over all cells the organizers' own sample_submission.tif has 7111787 NaN cells and GDAL_NODATA = nan two twins are published: -nan.tif (matches the template) and -zero.tif (all-finite, no nodata tag)

What the file contains

167597 pixels carry 1.0 (the greedy kernel-cover of the model's candidate traces); everything else inside the footprint is 0.0; outside the footprint it is NaN (-nan.tif) or 0.0 (-zero.tif). Nothing was copied from any earlier submission — the registry check reports the maximum rank correlation and 3 px overlap against every prior raster this checkout can read.
